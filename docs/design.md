# 日本株 買い候補ランキングツール 設計書

最終更新: 2026-10-31

## 1. 目的と前提

- 個人投資家（SBI証券）が、数日〜数週間保有する前提の買い候補を毎日ランキングする。
- ツールは候補を出すだけ。発注は手動で行う。
- SBI証券の画面の自動操作・スクレイピングはしない。保有株や取引履歴は、SBI証券から書き出したCSVを読み込む。
- 無料で使えるデータだけを使う。
- 実行環境はユーザーの Windows PC。

## 2. 確定した方針

| 項目 | 決定内容 |
|---|---|
| ニュース判定 | (c) 手動受け渡し。ツールが判定依頼ファイルを書き出し、ユーザーが Claude に渡し、返ってきた判定をツールが取り込む |
| 実行環境 | Windows PC |
| 対象銘柄 | 開発中は20銘柄。2026-11 から TOPIX500 相当（プライム × Core30/Large70/Mid400）＋売買代金の下限。履歴には範囲（universe 列）を記録し、事後検証では範囲の違う分を混ぜない |
| TDnet 適時開示 | 使う（非公式 WebAPI 経由） |
| ライブラリ | yfinance / feedparser / openpyxl / pytest を追加（JPX一覧が .xlsx になったため xlrd は外した）。anthropic は (c) では不要なので入れない（(a) に切り替えるときに追加） |

## 3. 制約（あらかじめ分かっている弱点）

1. **ニュース判定は手作業が残る。** 判定待ちの記事はスコアに入れず「未判定」と表示する。
2. **EDINET だけでは決算が遅れる。** 2024年4月に四半期報告書が廃止され、EDINET で取れるのは有価証券報告書と半期報告書のみ。PER は実績EPSベースになる。レポートには何月期のデータかを必ず出す。
3. **ニュースはバックテストできない。** 過去の RSS はさかのぼれないため、検証できるのはテクニカルとファンダメンタルのみ。ニュースは蓄積開始後に前向きに検証する。
4. **yfinance は非公式。** 仕様変更で止まる可能性があるため、Stooq を予備にする。どちらで取ったかは必ず記録する。
5. このスコアで勝てる保証はない。ランキングと実際の値動きを突き合わせる事後検証を重視する。

### 設計上の約束

- **取得と計算を分ける。** 計算側は「ある日付時点で手元にあるデータ」を受け取って点数を返すだけにする。バックテストでは過去データを1日ずつ流し込んで同じ関数を使う。
- **未来の情報を混ぜない。** 決算データは公表日で管理し、公表日より前の日付の計算には使わない。
- **黙って進めない。** 取得失敗・データの古さ・欠損はすべて `quality.py` に記録し、品質ログとレポート冒頭に出す。
- **CSV は UTF-8（BOM付き）で書く。** Windows の Excel でそのまま開けるようにするため。

## 6. スコアの仕組み

- テクニカル・ファンダメンタル・ニュースの3分野を、それぞれ 0〜100 点にする（50 が中立）。
- 各指標は `weights.yaml` に書いたルールで点数に変換する（例: RSI 30〜45 → +8）。
- 最終スコア = Σ(重み × 分野スコア)。
- データが欠けた分野は除いて、残りの重みで計算し直す。ランキングには欠損の印を付ける。欠損が多い銘柄は除外できる（しきい値は設定で指定）。
- 銘柄ごとに、効いた指標とその点数をレポートに出す。

## 7. ニュース判定（手動受け渡し）の流れ

1. `run_daily.py` がニュースを集め、未判定の記事を `output/news/YYYY-MM-DD_判定依頼.md` に書き出す。中身は固定の判定基準と、ID付きの記事一覧。
2. ユーザーがその内容を Claude に貼り付ける。
3. Claude が返した JSON を `data/news_judgments/inbox/` に保存する。
4. 次の実行時にツールが形式を検査して取り込む。形式違反は捨てて「判定失敗」と記録する。
5. 判定は記事ごとに保存し、同じ記事を判定し直さない。基準を変えたら `criteria_version` を上げる。

判定の出力形式:

```json
{"article_id": "...", "code": "7203", "category": "上方修正", "direction": 1,
 "strength": 2, "certainty": "確定", "reason": "通期営業利益を15%上方修正",
 "criteria_version": "v1"}
```

## 9. 事後検証の決まりごと

- 買値は「ランキングの翌営業日の始値」。ランキングは引け後に作るので、それより早くは買えない。
- 売値は「N営業日後の終値」（N = 1, 5, 10, 20）。営業日は TOPIX ETF（1306）の取引日で数える。
- 超過リターン = 銘柄の騰落率 − 同じ期間の TOPIX ETF の騰落率。配当・手数料は含めない。
- まだ N 営業日たっていない分は「未確定」、売買停止などで株価がない回は「株価欠損」として集計から外し、件数を出す。
- weights.yaml の version が違うランキングは、既定では混ぜない（最新 version だけを集計する）。
- 成績の信頼度の目安として、件数より「何日分あるか」と、日ごとに見た「上位 − それ以外」の差を重視する。

### 後付けの再現の限界

- 銘柄は「今の」対象銘柄を使うため、上場廃止になった銘柄などが入らず、成績が良く見えやすい。
- ニュースは過去にさかのぼれないので再現できない。
- 結果は毎日の分（history.csv）とは別のファイルに保存する。

## 10. 適時開示（段階5a）の決まりごと

- 取得: 非公式 TDnet WebAPI（やのしん）から日付ごとに1回（上限10,000件）。2026-05-14 のような決算集中日でも
  約2,300件で、上限に届かないことを確認済み。上限に届いた日は取りこぼしの可能性があるので使わない。
- 保存: data/raw/tdnet/日付.json。過去の日は二度取らない。今日と昨日は毎回取り直す（夜まで開示が増えるため）。
- 未来の情報を混ぜない: 基準日 D の点数には D の 23:59 までの開示だけを使う。毎日の実行では、実行時刻より後の開示は翌日分になる。
- 分類: タイトルに決まった言葉を含むかどうかだけで分ける（weights.yaml の disclosure）。方向が書かれていない
  「業績予想の修正」は点数0で表示だけする。
- 点数: 50 + Σ（決まりの点数 × 重み）。重みは開示当日が1で、decay_days（14日）で0になる。
- 欠損: 点数に使う期間に取得できなかった日があれば、その銘柄の適時開示は「欠損」とする。
- イベントスタディ: 開示前の最後の終値 → 買える最初の始値（反応・買う前）と、買える最初の始値 → N営業日後の終値（その後）を
  分けて TOPIX ETF との差を出す。t値は同じ日の開示を平均してから計算する。

## 11. XBRL（段階4a）の決まりごと

- TDnet の XBRL は約1か月で消える（それより古い zip は 404）。過去分は後から取れないので、毎日の実行で
  直近31日分のうち未取得のものを取り、主要な数字だけを data/xbrl/key_figures.csv に保存する。
- 対象は、対象銘柄の決算短信・業績予想の修正・配当予想の修正。取得結果は data/xbrl/fetch_log.csv に残し、
  ok と not_found は取り直さない。error は次回また取りに行く。
- 取り出す項目は、売上・営業利益・経常利益・税引前利益（IFRS）・純利益・1株利益・1株配当。会計基準ごとの
  項目名は xbrl_figures.ITEMS。見つからない項目は代用せず、取り出さない。
- 業績予想の修正は、修正前（PreviousMember）と修正後（CurrentMember）の予想を比べて、レポートに表示する。
  効果を確かめていないので、点数にはまだ使わない。
- 過去の検証には TDnet の XBRL が使えないため、J-Quants の無料プラン（過去の決算データ、12週間遅れ）を候補にする。

## 12. J-Quants と会社予想の変化（段階4b）の決まりごと

- J-Quants は V2（ダッシュボードで発行する APIキーを x-api-key ヘッダーに付ける）。2025-12-22 以降の登録者は V1 を使えない。
  APIキーは config/local/jquants_api_key.txt（GitHub に上げない）に保存する。
- 無料プランは約2年分・12週間遅れ・1分5回まで。決算データ（/v2/fins/summary）を銘柄ごとに1回ずつ取り、
  data/raw/jquants/fins_summary/銘柄コード.json に保存する。保存済みの銘柄は取り直さない。
- 業績予想の修正の書類には修正後の予想しかないので、同じ決算期の予想を書類の時刻順に追い、前の予想と比べる。
  四半期の決算短信の中で予想を変えた場合も同じ扱い。変わらなかった回は「据え置き」として比べる基準に残す。
- 本決算の F〜 の項目は来期予想とみなす（本決算の時点で今期は終わっているため）。実物で NxF〜 の項目が見つかればそちらを使う。
- 利益は営業利益 → 経常利益 → 純利益の順で、比べる2つがそろう最初のものを使う。元の数字が0以下なら出来事にしない。
- 12週間遅れなので、毎日のランキングには使わない（過去の検証専用）。毎日の分は TDnet の XBRL（段階4a）で集める。
- イベントスタディの t値は、出来事のあった日が10日分未満の種類では出さない。

## 13. ツールの役割の見直し（2026-11）

テクニカル指標（約500銘柄・1年）、適時開示のタイトル分類（1年）、会社予想の変化（J-Quants・2年）のどれでも、
「TOPIX500 を公開情報を見て翌朝に買い、数日〜数週間持つ」やり方で統計的に意味のある有利さは確認できなかった
（開示への反応は翌朝の寄り付きまでに済んでいる）。そこで、毎日のレポートの役割を「予測」から「材料の整理」に変えた。

- レポートの順番: データの問題 → 自分の注目銘柄 → 新しい開示（前営業日15時以降、種類別、決算・業績修正は XBRL の中身つき）
  → 値動きで目立った銘柄 → 参考: 機械的なランキング（予測力は確認できていない旨を明記）
- 自分の注目銘柄は config/local/my_stocks.yaml（GitHub に上げない）。SBI 証券の CSV の読み込み（段階6）は、
  売買の回数が少なく統計的な振り返りに使えないため見送った。
- ランキングの CSV と history.csv への記録は続ける（後付けの偏りのないデータで、後日もう一度検証するため）。
- 決算発表の中身: 利益の前年同期比、通期予想に対する進捗率、前回の予想からの変化（手元に前回の数字があるときだけ）。
